# 2026年10月 DIC AI 工程化体系评审报告 · aic试点反馈报告

对 [DIC-PM-AI-Engineering](https://github.com/rosetta-guo-fyaic/DIC-PM-AI-Engineering) 工程化体系的实测评审：用一个 DEMO 小系统作载体，从立项一路走到发布，全程留痕，回答三个问题——**体系能不能用？哪里好用？哪里要改？**

**验证方式一句话**：五个 AI 角色按体系规则分工（OD / 产品经理 / 研发 / 测试 / 产品总监），走完 OD 工作区 → 零~四号仓库 → 代码仓 → 发布共七段流程，四道评审门禁全部执行。产物全部公开：[项目文档仓](https://github.com/rosetta-guo-fyaic/minhuo-kantai-doc)（tag `baseline/v1.0.0`）｜[项目代码仓](https://github.com/rosetta-guo-fyaic/minhuo-kantai-code)（tag `release/v1.0.0`）。

> 本报告已与 **AIC 评议**（技术负责人 Veil，[fyaic/dic-ai-engineering-review](https://github.com/fyaic/dic-ai-engineering-review)，私有协作仓）交叉印证合并：两份评审方法互补（他们静态评议工具仓脚本、我们动态实测全流程），逐项对照与合并改法见 [05-与AIC评议的交叉印证.md](05-与AIC评议的交叉印证.md)。

## 评审结论

**体系可用：链路全程跑通（自动化测试 61+26 项全过、0 产品缺陷），但直接推广前有 31 项断点要处理，其中两类建议优先修。**

### 做得好的地方

1. **全链路可执行**——七段流程无跳段，每段有产出、有收口提交、有留痕
2. **评审门禁真实有效**——四轮评审抓出 10 项产出方自己发现不了的缺陷，全部闭环
3. **模板让产出结构一致**——127 份文档同构零漂移，换人接手不用猜结构
4. **版本治理闭环**——tag 里载着评审结论原文，冻结时刻任何人可核验
5. **范围控制有效**——10 项需求中 5 项范围外全部显式登记排除原因，零 scope 漂移

→ 逐条证据见 [01-做得好的地方.md](01-做得好的地方.md)

### 需要改进的地方

1. **小项目被迫穿大衣服**——8 项断点指向「简化路径没有合法地位」，小需求要么硬走重流程、要么违规绕行
2. **编号体系互相打架**——5 项跨仓编号冲突（同一个编号两个含义）
3. **追溯与门禁靠自觉**——4 项追溯断点，无机器校验；AIC 评议另证实工具仓范围检查脚本自身漏检暂存/未跟踪变更（TECH-001，我方已复跑确认）
4. **Skill 绑死特定运行器**——换一个 AI 工具链就失效，「可复制」目标受阻
5. **验收证据可信度无制度保障**——实测抓到一次「测试报告声称测了、实际没测」

→ 改法与优先级见 [02-需要改进的地方.md](02-需要改进的地方.md)；与 AIC 评议合并后的统一改法视图见 [05-与AIC评议的交叉印证.md](05-与AIC评议的交叉印证.md) §4

## 评审边界（读结论前先知道）

- **载体是 DEMO**（敏货看台，敏感货可接性看板）：业务命题来自真实访谈，但数据全虚构（22 品类均带「样例」标注），不接任何真实信源。评审对象是**流程**，不是这个系统好不好用。
- **没有真人参与**：所有「人工确认」环节为材料或角色代位（文档中逐处显式标注）；「AI 生成 + 人工确认」里「人」的那一半未经真实验证——这是本评审最大的边界。
- **单版本、单人单机**：版本迭代码（1.1 承接、基线后变更、hotfix）只预留未实测；多人 Git 并行未覆盖（AIC 评议同样未实测，双方在此一致诚实）。
- 本报告由 AI 产出，经独立评审子代理否定性评审后定稿（评审记录在本仓 Git 历史）。
